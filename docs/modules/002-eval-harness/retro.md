## 1. 做出了什麼

一個與領域無關的 eval 工具:對資料集呼叫模型、打分(確定性檢查 + LLM 評審)、比較兩次執行,

## 3. 架構決策(詳見 ROADMAP 決策表)

- **D-029** 第一版只評估「一次 LLM 呼叫」;輸入與輸出用 enum 留擴充點 → 003、004 才知道 agent 與檢索的型別,現在設計是用猜的。
- **D-030** 資料集分兩層:手寫公開的進 git,真實對話放 repo 外(700 / 600)→ 公開版讓 CI 與別人 clone 後有東西可跑。
- **D-031** 確定性檢查 + 逐條「通過 / 不通過」的 LLM 評審;評審的輸出與被評的回答都當不可信輸入。
- **D-032** `run` 與 `score` 分兩階段、一次執行一個目錄、`compare` 用固定種子的 paired bootstrap → 換評審不必重付產生的錢。
- **D-033 / D-034 / D-035** 直接用 `llm` 套 Alias + Retry、不套 Record;事前估價與 `--budget`;並列全部通過率與部分得分、A/A 雜訊底線、打分設定不一致就拒絕比較。
- 實作時補上的:沒評的標準記成 `Skipped`、統計時算 0 分(2026-11-09);`--budget` 在送出之前檢查,所以可能超出「並行數 × 一次呼叫」。

## 4. 第一次真的比較:一個沒有贏家的結果

`rust-basics`,Haiku 5.5 對 Sonnet 5.5,評審 Sonnet 5.5:兩邊 54 個判決全過,差 +0.0,翻轉 0 題。數字與解讀在 README。帶走的是:

1. **全過 = 沒有資訊。** 這份資料集和評審合起來分不出兩個模型。「看不出差異」是證據不夠,不是「一樣好」。
2. **全過有兩種成因,資料分不開:題目太簡單,或評審太鬆。** 要分辨得另外做校準(故意餵錯的回答、換不同家的評審),這是 eval 自己的測試,不是模型的測試。
3. **`[+0.0, +0.0]` 是方法在零變異時的退化結果。** 讀成「量得很準」是錯的。這是顯示方式的問題,已記進 ROADMAP 待辦,等使用者決定。
4. **費用的認知被修正了。** 執行費差 20 倍(就是單價比,兩邊輸出 token 幾乎一樣),連評審一起算只差 2.3 倍,因為評審是固定成本(約 $0.05,佔 `cheap` 總成本的 93%)。
   D-034 當初估「評審約是產生回答的 20 倍」,實測是 14 倍(12 題、effort low)。估計值寫進決策時沒有標註是估計,README 已改成實測值。
5. **對專案:** 便宜模型在簡單題上不輸貴的,與「飛輪要贏過直接用 Haiku」的假設一致;但不能推論成 Haiku 一般來說和 Sonnet 一樣好。

## 5. 學到的教訓

1. **測試全綠,真實世界還是找得到 bug。這次有三個,共同點是「測試和產品共享同一個盲點」。**
   - `$-0.0000`(`89a18c4`):浮點 `Sum` 從 `-0.0` 起算,單元測試用 `==` 比(`-0.0 == 0.0`),只有讀「印出的文字」的 E2E 抓到。
   - 半行(`583e4ab`):崩潰後最後一行寫到一半,用換行封住會讓檔案中間出現壞行,之後每次接續都讀不了。
   - **`finished_at` 等於 `started_at`(尚未修,見 ROADMAP):** 單元測試注入時間,方便也確定;但「在哪裡取時間」本身是邏輯,
     `main` 在工作開始前取一次,同一個值傳給開始與結束。第一次真的執行,看 `meta.json` 才發現。
     注入的值讓測試好寫,也把「值從哪來」這個問題移出了測試的視線。
2. **假資料太乾淨,運算就測不出來。** 假評審回報 0 個 cache token,所以 `+=` 換成 `-=` 沒人發現(`7a619be`)。
   fake 的回傳值要讓每個欄位都不一樣、非 0。
3. **Mutants (diff) 在 push 後補了真缺口。** 第 7 步之後一次補 10 個 compare 缺口(`adedd50`),其中一個還化簡了程式(等價的分支直接移掉)。
   D-036 把 cargo-mutants 搬上 CI 之後,回饋變成 push 後,補測試放在下一個 commit,節奏可以接受。
4. **成本要先估再控,估計要用量測校正。** `--budget` 與 `--dry-run` 讓第一次真的呼叫可以放心按下去($0.177 對上限 $4.10);
   但「約 20 倍」這種數字寫進文件之前要先量過(CLAUDE.md:效能主張要有數字撐)。
5. **雲端的 API key 流程可行。** key 只放環境變數,用 `[[ -v 名稱 ]]` 確認有設定,包裝腳本寫成檔案再執行,
   指令文字裡沒有 `$..._KEY`,guard hook 沒有被觸發也沒有被繞過;key 沒有出現在任何輸出。
   代價:執行結果放在容器的資料目錄,session 結束就沒了,所以重要的數字必須寫進 README。
6. **E2E 的假 Claude 夠像。** 24 次產生與 24 次評審,沒有任何格式或協定錯誤(兩邊都是 `end_turn`、評審回覆都通過嚴格驗證)。
   這是一次樣本,不證明格式不會變;live test(`#[ignore]`)還是要定期手動跑。

## 6. 下一部分要帶走的

- **用 eval 做決定之前要先補三件事**(ROADMAP 待辦):有鑑別力的題目(含會讓 Haiku 失敗的)、雜訊底線、評審校準。
- **「取時間」這類不確定性的來源,測試要涵蓋「在哪裡取」**,不只是「取到之後怎麼用」。修 `finished_at` 時順便做。
- **003 的提醒**(Harness² 清單,見 ROADMAP 想法池):方法 / 執行器 / benchmark 三者分開;評估有網路工具的 agent 時要限制它能連的地方(公開題目在 GitHub 上)。
- eval 與 llm 各有一份「私有目錄、寫了一半的行」的程式;第三個使用者出現(006)時抽成共用工具。

## 7. 文章大綱

**標題:〈怎麼知道「這樣改比較好」?從零寫一個誠實的 LLM eval harness〉**

1. Eval 不是測試:確定性的 pass/fail 與對資料集打分的差別
2. 評審也會錯:逐條判斷、隨機分隔標記防 prompt injection、嚴格驗證回覆、自我偏好警告
3. 比較要誠實:paired bootstrap、A/A 雜訊底線、設定不一致就拒絕比較
4. 錢:事前估價、預算上限,以及「評審才是費用大頭」
5. 第一次真的比較:兩個模型都全過——一個沒有贏家的結果教了什麼(天花板效應、`[+0.0, +0.0]` 的陷阱)
6. 測試全綠仍有的 bug:`-0.0`、半行、`finished_at`
7. 下一步:有鑑別力的資料集與可信的評審
